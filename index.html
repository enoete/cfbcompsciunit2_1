An abstract data type is defined by its operations, not by its storage.

A stack promises you push and pop. A queue promises enqueue and dequeue. Neither promises an array. That distinction is the whole chapter — and by the last section you will take one of these apart and rebuild it out of something completely different, without changing a line of the code that uses it.

You'll build up to that diagram. By the end you'll be able to redraw it from memory and explain every arrow in it.

0

What an abstract data type actually is

Written out properly: an abstract data type is a data structure described by the operations you may perform on it and the rules those operations follow — with no mention of how the data is actually stored.

The word doing the work is abstract. You are told what the thing does. You are deliberately not told how.

Think of an ATM

You know the operations: deposit, withdraw, checkBalance. You have no idea whether the money is in a drawer, a safe, or a vault downstairs — and you don't need to. The operations are the contract. The storage is somebody else's problem.

That's an ADT. A stack promises you push and pop. Whether it's built from an array or from linked nodes is an implementation detail you can swap out without changing a single line of the code that uses it. You'll do exactly that swap at the end of this guide.

Three ADTs, in the order that makes them easiest to learn:

  1. Stack — add and remove at one end only. One marker to track.
  2. Queue — add at one end, remove from the other. Two markers.
  3. Linked list — add and remove anywhere, any size. Every node tracks its own neighbour.

Each one is the previous one with a restriction lifted. Stacks and queues are about discipline — giving up freedom on purpose so the structure makes you a promise. Linked lists are about arrows, and they are where most people get stuck.

So take them in that order. Done this way, the linked list arrives as the solution to a problem you have already run into yourself, rather than as a wall of pointer syntax on the first day.

Stacks

A stack is a list where you deliberately throw away most of your freedom: you may only add and remove at one end. That end is called top.

The plate pile in the canteen

Clean plates go on the pile. You take the plate off the top. The plate at the bottom has been there since Monday and nobody has touched it.

That's LIFO — last in, first out. The last plate on is the first plate off, and you physically cannot reach the third plate down without lifting the two above it.

Only four operations matter, and the whole structure is one array plus one integer:

LAB 1

Push, pop, overflow, underflow

This stack holds 5 items. top starts at −1, which is the C way of saying "empty" — there is no index −1, so the value is safely meaningless until something is pushed.

top = -1   (stack is empty)
Two states to trigger on purpose

Push six values — the sixth is refused. That's overflow, caught by if (top == MAX-1). Now pop an empty stack: that's underflow, caught by if (top == -1). Both guards belong in every stack you write, and forgetting either one is how a program crashes on the day it matters.

The code, and why top moves when it does

/* the entire data structure */
#define MAX 5
int stack[MAX];
int top = -1;          // empty

void push(int item)
{
    if (top == MAX-1) {
        printf("Overflow\n");
        return;
    }
    ++top;                 // move up first
    stack[top] = item;     // then write
}

top always points at the last item written, never at the next free slot. So on the way in you move up before writing. The shorthand stack[++top] = item; means exactly the same thing in one line.

int pop()
{
    if (top == -1) {
        printf("Underflow\n");
        return -1;
    }
    int item = stack[top];  // read first
    --top;                  // then move down
    return item;
}

int peek()  { return stack[top]; }
int isEmpty(){ return top == -1; }

Notice pop doesn't erase anything. The old value still sits in the array — it is simply above top now, so it is unreachable and the next push overwrites it. In a stack, "deleting" and "making unreachable" are the same act.

Stacks at work

Stacks are not an academic curiosity. You have used four of them today without noticing.

Undo

Every edit gets pushed. Ctrl+Z pops the most recent one. That's why undo always reverses your latest action, never an older one — the structure literally cannot reach further down.

The browser back button

Each page you visit is pushed. Back pops. Open a new link from the middle of your history and the forward stack is thrown away — because a stack only has one reachable end.

The call stack

When main calls push, the return address is pushed onto a stack. When push finishes, it pops. Infinite recursion pushes forever — and the error message you get is literally "stack overflow".

Matching brackets

Every compiler and code editor checks your { } with a stack. Open bracket: push. Close bracket: pop and check it matches. It is a five-line algorithm and it is used billions of times a day.

Application 1 — the bracket checker

This is the algorithm your compiler runs on your C file before it tells you off. It is worth understanding completely, because it shows why LIFO is the right shape: the bracket you must close next is always the most recently opened one.

int balanced(char s[])
{
    top = -1;                                   // start with an empty stack
    for (int i = 0; s[i] != '\0'; i++)
    {
        char c = s[i];

        if (c == '(' || c == '[' || c == '{')
            push(c);                          // remember what we opened

        else if (c == ')' || c == ']' || c == '}')
        {
            if (isEmpty()) return 0;        // a closer with nothing open
            char open = pop();
            if (!matches(open, c)) return 0;  // wrong kind of closer
        }
    }
    return isEmpty();                       // leftovers = something never closed
}

Three ways it can fail, and each maps to one line above: a closer with an empty stack, a closer that doesn't match what popped out, or a non-empty stack at the end.

Application 2 — reversing anything

A stack reverses whatever you feed it, for free, just by pushing everything in and popping everything out. No loop counters, no swapping, no working backwards through indices.

void reverse(char s[])
{
    top = -1;
    int n = strlen(s);

    for (int i = 0; i < n; i++) push(s[i]);   // last char ends up on top
    for (int i = 0; i < n; i++) s[i] = pop(); // so it comes out first
}

Application 3 — a calculator that never needs brackets

Punch 3 + 4 × 2 into an ordinary calculator and you need to know that × happens before +, or you get the wrong answer. Some real calculators — classic HP models, and every compiler evaluating an expression internally — sidestep the whole problem by working in Reverse Polish Notation (RPN): numbers first, operator after. 3 4 + means "3, 4, add them." There is no ambiguity to resolve and no bracket to balance, because the order you write the tokens in is the order they get used. A stack evaluates it in one pass, left to right, and never looks back.

Handing ingredients to a chef one at a time

You hand the chef a carrot, then an onion. The chef doesn't cook until you say "combine" — and when you do, the chef reaches for the two things closest to hand: the onion first, then the carrot underneath it. That's it. That's the entire algorithm. Numbers get set down on the counter (pushed). An operator means "combine the top two things on the counter," and the result goes right back onto the counter for whatever's next.

Notice applyOp(a, b, op) takes two numbers in a specific order: a first, b second, computing a op b. Keep that order in mind — the next cell has to hand them over correctly, and it's the one place this whole program can quietly go wrong.

In [2]
int evalRPN(char *expr)
{
    top = -1;                                    // empty stack, reusing Lab 1's variable
    char *token = strtok(expr, " ");      // split on spaces

    while (token != NULL)
    {
        if (isOperator(token[0]) && token[1] == '\0')
        {
            int b = pop();                       // the number pushed MOST recently
            int a = pop();                       // the one pushed before it
            push(applyOp(a, b, token[0]));
        }
        else
            push(atoi(token));               // it's a number — convert and push

        token = strtok(NULL, " ");
    }
    return pop();                              // the one value left is the answer
}
markdown

Read b = pop() then a = pop() again, slowly. The stack is LIFO, so the second number you pushed is the first one back out. For + and * the order never matters. For - and / it is everything.

The bug that only shows up on subtraction

Swap the two lines to a = pop(); b = pop(); and addition and multiplication still work — they don't care about order, so your test cases pass and you ship it. Then someone runs 10 3 - expecting 7 and gets −7 instead, because a and b got the numbers backwards. Always pop into b first. It is the operand closest to the top, which means it is the one that arrived most recently — and in a – b, that's the one being subtracted.

Queues

Same idea as a stack, one change: you add at one end and remove from the other. That single change flips the behaviour completely, and costs you a second marker.

The line at the bank

You join at the back. You are served from the front. Whoever has waited longest goes first, and anyone who joins at the front is going to hear about it.

That's FIFO — first in, first out. A queue needs front (who is being served) and rear (where the next person joins). A stack needed one marker because both ends were the same end.

StackQueue
Addpush() at topenqueue() at rear
Removepop() from topdequeue() from front

Fair?No — the bottom item may wait foreverYes — everyone is served in arrival order

That "fair?" row is the reason both structures exist. When order of arrival is a promise you're making to someone — a printer, a customer, a download — you need a queue. When you want the most recent thing first, you need a stack.

Enqueue, dequeue, and a problem nobody warns you about

Add a few values, then remove a few. Keep going and watch the left-hand side of the array.

front = -1, rear = -1   (queue is empty)

The code

#define MAX 8
int queue[MAX];
int front = -1, rear = -1;

void enqueue(int data)
{
    if (rear == MAX-1) {
        printf("Queue full\n");
        return;
    }
    if (front == -1) front = 0;  // first arrival
    rear++;
    queue[rear] = data;
}
int dequeue()
{
    if (front == -1 || front > rear) {
        printf("Queue empty\n");
        return -1;
    }
    int data = queue[front];
    front++;
    if (front > rear)            // served the last one
        front = rear = -1;       // reset to empty
    return data;
}

That reset in dequeue matters. Without it, an emptied queue leaves front and rear stranded near the end of the array, and the next enqueue reports "full" on a completely empty queue.

The drift problem, and circular queues

You probably saw it in Lab 5. Dequeued cells are dead: front only ever moves right, so slots at the start can never be reused. Eventually rear hits the end of the array and the queue reports "full" while half of it sits empty and wasted.

A queue that eats its own array

Imagine a bank line drawn on the floor with chalk. Every time someone is served, the front of the line moves one step forward — but nobody is allowed to step back into the empty chalk squares behind them. After twenty customers the whole line has drifted out of the building.

The fix is to bend the chalk line into a circle. Run off the end, come back to the start.

One operator does it. When a marker would run off the end, wrap it to 0 with the modulo operator:

rear  = (rear  + 1) % MAX;    // 7 -> 0 when MAX is 8
front = (front + 1) % MAX;

But now a new problem appears. In a circle, front == rear happens when the queue is full and also when it is empty — the markers meet either way. The simplest fix is to keep a count of how many items are actually stored:

int queue[MAX];
int front = 0, rear = -1, count = 0;

void enqueue(int data)
{
    if (count == MAX) {
        printf("Queue full\n");
        return;
    }
    rear = (rear + 1) % MAX;   // wrap
    queue[rear] = data;
    count++;
}
int dequeue()
{
    if (count == 0) {
        printf("Queue empty\n");
        return -1;
    }
    int data = queue[front];
    front = (front + 1) % MAX; // wrap
    count--;
    return data;
}

Where circular queues actually run

Your keyboard

Keystrokes land in a small circular buffer while the program is busy. Type faster than the program reads and the buffer fills — that's the beep, and the lost characters.

Streaming and playback

Audio and video players keep a circular buffer of decoded frames. The decoder writes at the rear, the speaker reads from the front, round and round, forever, in a fixed amount of memory.

Print spoolers

Jobs queue in arrival order. Fixed memory, no drift, no job skipping the line — exactly the promise a queue makes.

Round-robin scheduling

An operating system gives each process a slice of CPU time, then sends it to the back of the queue. Circular by nature: the list of processes never ends, it just cycles.

Application — the doubles stand at the savannah

Lunchtime. One vendor, one line, a handful of spaces to park an order while it waits to be cooked. Every customer gets a ticket number when they join, and tickets get served in the exact order they were handed out — no cutting the line, no favourites. That promise is a queue's entire job description, and a circular one is the right tool because the stand runs all day: it cannot afford section 4's drift problem eating one array slot per hour.

void enqueueOrder(char *item)
{
    if (count == MAX) {
        printf("Sorry, the line is full — wait for a gap.\n");
        return;
    }
    rear = (rear + 1) % MAX;                     // wrap, exactly like section 4
    line[rear].ticket = nextTicket++;
    strcpy(line[rear].item, item);
    count++;
    printf("Ticket #%d — %s joins the line.\n", line[rear].ticket, item);
}

void serveNext(void)
{
    if (count == 0) { printf("Nobody's waiting.\n"); return; }
    printf("Serving ticket #%d: %s\n", line[front].ticket, line[front].item);
    front = (front + 1) % MAX;
    count--;
}

The wall you just hit

Go back to Lab 1 and push a sixth value. It is refused. Not because the computer is out of memory — your machine has gigabytes free — but because #define MAX 5 was decided before the program ever ran.

That is the fundamental limit of an array. Its size is fixed at compile time. Which leaves you choosing between two bad options:

  • Declare it too small, and the program fails on a busy day.
  • Declare it too big, and you waste memory permanently to handle a case that almost never happens.

There is a second, quieter problem. Inserting at the front of an array means shifting every other element right, one at a time. For 10 items that's nothing. For 10,000 it's 10,000 moves for a single insertion.

So here is the question the next section answers

What if we didn't ask for all the memory up front? What if each item were allocated the moment it was needed, wherever there happened to be room — and each one simply remembered where the next one lived?

Then the structure grows to exactly the size it needs, whenever it needs to, and inserting at the front means changing two arrows instead of shifting ten thousand values.

That is a linked list. Everything in the rest of this guide exists to pay for those two sentences.

Array vs linked list, side by side

Before any code, three demonstrations. Each one sets the two structures the same task and lets you watch them do it. Two of them the linked list wins easily. One of them it loses badly — and that one matters just as much, because a structure that won everything wouldn't need an alternative.

To make this concrete, pretend your whole computer has twelve memory slots. Real machines have billions, but the rules are identical, and twelve fits on a screen.

Demo A — the shape of the space you need

Here's the rule that explains almost everything: an array must live in one unbroken run of slots. Ten items means ten slots in a row, because the computer finds a[7] by starting at the first slot and counting forward seven. Break the run and that arithmetic stops working.

Linked nodes have no such rule. Each node can live anywhere, because each one carries the address of the next.

Why the array can jump and the list cannot

An array is a street of identical houses, numbered from zero. To reach number 6 you don't walk past the first five — you know house 6 is six house-widths from the start, so you go straight there. One calculation: start + 6 × size. That works only because the houses are the same size and all in a row.

A linked list is the scavenger hunt. The cards are scattered all over campus and the only way to learn where card 6 is, is to read card 5 — and to find card 5 you must read card 4. There is no formula, because there is no pattern to the addresses. That is the exact price you paid for being allowed to store them anywhere.

So which one, when?

Neither wins. They fail in opposite directions, and choosing well is the actual skill:

One sentence to keep

Arrays are fast to reach into but rigid. Linked lists are flexible but slow to reach into. Pick based on whether your program does more looking things up or more growing and editing.

Linked lists

The scavenger hunt

Forget code for a minute. Picture a scavenger hunt around campus.

You're handed a slip of paper that says "start at the library." At the library you find a card. On the card: a prize, and one line of writing — "next clue: the canteen." At the canteen, another card: a prize, and "next clue: the car park." At the car park: a prize, and "this is the last one."

Map it one to one
  • Each card = a node
  • The prize on the card = the data
  • "next clue: the canteen" = the next pointer
  • The slip in your pocket saying where to start = head
  • "this is the last one" = NULL

Three consequences fall straight out of that picture, and they explain nearly everything students find strange about linked lists:

  1. The cards are scattered. The library and the canteen aren't next to each other. Nodes are scattered in memory too — which is exactly how the structure escapes the fixed-size array. It never needs one big contiguous block.
  2. You can't skip. To reach the third card you must visit the first and second. There is no list[2]. That's the price you pay for the flexibility, and it's why traversal is always a loop.
  3. Lose the slip in your pocket and the whole hunt is gone. Every card is still out there; you just can't reach any of them. Lose head and you lose the list, permanently. Hold onto this one — it comes back in about five minutes.

Anatomy of a node

A node in C is a struct holding two things: a value, and an address.

struct node {
    int  data;              // the prize on the card
    struct node *next;      // where the next card is
};

struct node *head = NULL;   // the slip in your pocket. Empty list = NULL.

That second line looks impossible the first time you see it: a struct containing a pointer to its own type. It works because next does not store a node — it stores an address, and an address is just a number. A card does not contain the canteen. It contains the word "canteen."

In every diagram below, the white cell is data and the blue cell is next. Blue always means "an address lives here."

The rule for ->

-> means "follow the arrow, then look inside." So head->next->data is three moves: go to head, follow one arrow, read the data. Every extra ->next is one more step down the hunt.

Creating a node: what malloc really does

Declaring a pointer does not create a node. This is the single most common misunderstanding in the topic:

struct node *newNode;   // an EMPTY luggage tag. Points nowhere useful.

newNode = (struct node*)malloc(sizeof(struct node));
// NOW a real box exists somewhere in memory,
// and the tag has that box's address written on it.

malloc asks the operating system for a chunk of memory big enough for one node and hands back its address. If memory has run out it returns NULL instead, which is why every allocation is followed by a check.

This is also the answer to the size wall: malloc runs while the program is running. The list grows one node at a time, on demand, for as long as the machine has memory.

Insert at the front — where the order matters

You have a list. You want a new node at the very beginning. Two pointers must change:

  1. The new node's next must point at the old first node.
  2. head must point at the new node.

Two lines. Two possible orders. Only one works — and if you pick wrong, the program still compiles, still runs, and quietly destroys your entire list.

Back to the scavenger hunt

You want to add a new first stop — the gym — before the library. The slip in your pocket currently says "library."

Write "library" on the gym card first, then change your slip to "gym": everything is fine. But change your slip to "gym" first, and you have erased the only record of where the library was — while the gym card is still blank. The whole hunt is gone and there is no way to recover it.

The rule to memorise

Always attach the new node to the list before you move head. More generally: never overwrite a pointer until something else is already holding what it pointed at. Every pointer bug in this topic is a version of that one sentence.

The complete function
void insertFront(int data)
{
    struct node *newNode = (struct node*)malloc(sizeof(struct node));

    if (newNode == NULL) {
        printf("Out of memory\n");
        return;
    }

    newNode->data = data;
    newNode->next = head;   // 1. attach to the list FIRST
    head = newNode;         // 2. then move head
}

Bonus: this works perfectly on an empty list with no special case at all. If head is NULL, then newNode->next = head sets next to NULL — exactly right for a one-node list. That elegance is not luck; it is why insert-at-front is the cheapest operation a linked list has, and why a linked-list stack pushes in three lines.

Traversal — walking the list

Everything else you will ever do to a linked list — printing, searching, counting, inserting at the end, deleting the last node — begins by walking down it. The walk is always the same three pieces:

void display()
{
    struct node *temp = head;      // 1. start at the beginning
    while (temp != NULL) {        // 2. keep going while there's a card
        printf("%d -> ", temp->data);
        temp = temp->next;         // 3. take one step
    }
    printf("NULL\n");
}

temp = temp->next is the step. Read it as: "read the next-clue on the card I'm standing at, and go stand there." It never moves the list; it moves you. This is also why you use temp and not head — walk with head and by the end of the loop head is NULL and your list is gone.

The off-by-one that catches everyone

There are two loop conditions and they stop in different places. Swap them by accident and you get a crash or a missing node.

  • while (temp != NULL) — walks past the last node and ends holding nothing. Use it to visit every node: printing, searching, counting.
  • while (temp->next != NULL) — stops on the last node. Use it when you need to hold the last node: inserting at the end.

Searching — traversal with a question attached

Once you can walk, searching is the same loop with an if inside it. This is the whole function:

int search(int key)
{
    struct node *temp = head;
    int position = 0;

    while (temp != NULL) {
        if (temp->data == key) return position;   // found it
        temp = temp->next;
        position++;
    }
    return -1;                                    // walked off the end
}

Compare that to an array, where you could jump straight to a[position]. In a linked list there is no jumping — finding item 500 means 500 steps. That is the trade you accepted in exchange for unlimited growth.

Deleting nodes

Deleting is two jobs, always in this order: re-route the arrows around the node, then hand the memory back with free(). Do it the other way round and you are following a pointer into memory that is no longer yours.

Delete the first node

The easy one. You need a temporary pointer for exactly one reason: once head moves forward, nothing remembers the old first node — and you still need its address to free it.

Delete the last node — why one pointer isn't enough

Here is the problem that makes this harder than it looks. To delete the last node you must set the second-to-last node's next to NULL. But a singly linked list only goes forward — once you are standing on the last node, there is no way back to the one before it.

Why two pointers

You're walking the scavenger hunt and you want to remove the final card. When you arrive at it you need to go back and cross out the "next clue" line on the previous card — but the cards only point forwards. You have no idea where you came from.

The fix is to walk with a friend one step behind you. When you stop, your friend is standing exactly where you need them. That friend is the second pointer.

LAB 14

Two pointers walking together

toDelete leads, secondLast follows one step behind. Step until toDelete->next is NULL, then cut.

Ready.
The full function
void deleteLast()
{
    struct node *toDelete, *secondLast = NULL;

    if (head == NULL) { printf("List is empty\n"); return; }

    toDelete = head;
    while (toDelete->next != NULL)   // stop ON the last node
    {
        secondLast = toDelete;       // friend catches up...
        toDelete = toDelete->next;   // ...then you step forward
    }

    if (toDelete == head)            // only one node in the list
        head = NULL;
    else
        secondLast->next = NULL;     // cut the link

    free(toDelete);                  // hand the memory back LAST
}

Order inside the loop matters. secondLast = toDelete; must come before toDelete = toDelete->next;. Swap them and your friend ends up standing on the same card as you, which defeats the whole point.

What free() does and doesn't do

free(p) returns the memory to the system. It does not change p — the pointer still holds the old address, and is now called a dangling pointer. Using it after the free is undefined behaviour: sometimes it works, sometimes it crashes, sometimes it silently corrupts something three functions away. Set it to NULL after freeing and the bug becomes an honest crash instead of a mystery.

Doubly and circular linked lists

Everything so far has been a singly linked list: one arrow per node, pointing forward, ending at NULL. Change what that arrow situation looks like and you get two more structures — each solving a problem the singly linked list handles badly.

You have already felt both problems in this guide, which is why they're here rather than in a footnote.

Singly linked — the limitation, restated

Remember Lab 14, deleting the last node. You had to drag a second pointer behind you the whole way down the list, for one reason: once you're standing on a node, there is no way back. The arrows only point one way. To find out what came before a node, you must start again from head.

The doubly linked list

The fix is almost insultingly simple: give every node a second pointer that points backwards.

struct node {
    int  data;
    struct node *next;   // the node in front
    struct node *prev;   // the node behind      <-- the only new line
};

Now the list is a chain you can walk in either direction. The first node's prev is NULL and the last node's next is NULL — both ends are marked.

Train carriages

A singly linked list is a line of carriages where each one is coupled to the carriage in front, and the coupling only works in that direction. Standing in carriage 4, you can walk forward, but there is no door behind you.

A doubly linked list couples every carriage at both ends. Now you can walk to the front or the back from anywhere. That's the whole idea. Everything else is bookkeeping.

LAB 15

Walk both ways

Blue arrows on top are next. Amber arrows underneath are prev. Move temp in either direction — and notice the Back button is something a singly linked list simply cannot offer.

What the second pointer costs you

Two things, and both show up in exams.

Memory. Every node now carries an extra address. On a list of a million small nodes that is a million extra pointers of overhead, for nothing but convenience.

Twice the arrows to get right. Inserting into a singly linked list touches 2 pointers. Inserting into a doubly linked list touches 4, and forgetting one leaves the list walkable forwards but broken backwards — a bug that hides until someone presses Back.

Insert at the front, doubly

Same principle as before — attach before you move — but there are now four assignments, and one of them needs a guard.

void insertFront(int data)
{
    struct node *n = (struct node*)malloc(sizeof(struct node));
    n->data = data;

    n->next = head;                    // 1. new node points forward at the old first
    n->prev = NULL;                    // 2. nothing is before the new first node

    if (head != NULL)                  //    guard: the list might be empty!
        head->prev = n;                // 3. old first node points back at the new one

    head = n;                          // 4. move head, last as always
}

Line 3 is the one people forget. Without it the forward chain is perfect and the backward chain is broken, so the list prints correctly and then crashes the first time anyone walks it in reverse.

Where doubly linked lists actually run

Browser history

Back and Forward are prev and next. A singly linked list could give you one of those buttons. It could never give you both.

Undo and redo

A plain undo stack cannot redo, because popping throws the action away. A doubly linked list of edits lets the cursor move back and forward through history without losing anything.

Music and video players

Next track and previous track, plus removing a song from the middle of the queue without walking from the start to find what preceded it.

Text editors

A line of text as a chain of characters. The cursor moves left and right one node at a time — and deleting needs the node before, which is right there.

The circular linked list

Different change, different problem. Take a singly linked list and, instead of the last node pointing at NULL, point it back at the head.

/* the struct is unchanged — only the last node's next is different */
lastNode->next = head;    // instead of NULL

There is now no end. Keep following next and you come back around to where you started, forever.

Passing a plate around a table

Four people at a table pass a dish to the person on their left. When it reaches the last person they pass it back to the first. Nobody is "the end" — the last seat simply connects to the first, and the dish can go round all night.

That is exactly what a circular list is for: things that cycle rather than things that finish.

LAB 17

Why your normal loop condition breaks

Here is the trap. Run the familiar traversal on a circular list and watch what happens.

The rule for circular lists

NULL never appears, so while (temp != NULL) never becomes false. The program does not crash — it just prints forever, which in an exam is worse, because it looks like it should work.

You stop when you get back to where you started instead. And it must be a do...while, not a while: on entry temp already equals head, so a plain while (temp != head) would exit immediately and print nothing.

struct node *temp = head;
if (head == NULL) return;        // empty list still needs its guard

do {
    printf("%d ", temp->data);
    temp = temp->next;
} while (temp != head);          // stop when we come back around

Where circular lists actually run

Round-robin CPU scheduling

The OS gives each process a slice of time then moves to the next. After the last process it must return to the first — and it never stops. The process list has no natural end, so it shouldn't have a NULL.

Turn order in games

Four players, play passes round the table and back to player 1. A circular list means the code never needs an "if we ran out of players, start again" special case — the structure handles it.

Image carousels and slideshows

Press Next on the final photo and you land on the first. Make it circular and doubly linked and Previous wraps backwards too.

Circular buffers

The keyboard and streaming buffers from section 4 are the same idea — you already met it as an array with % MAX. This is the pointer version of that wrap.

And yes, you can combine them

A doubly linked circular list has both: every node points both ways, and the two ends join up. Next on the last item wraps to the first, Previous on the first wraps to the last. That is what a real media player's shuffle-and-repeat queue usually is — and it is also how many operating systems hold their list of running processes.

Putting it together

The six bugs that cost the most marks

Every one of these compiles cleanly.

1. Moving head before linking

head = newNode; then newNode->next = head; makes the node point at itself and orphans the whole list. Attach first, always.

2. Forgetting newNode->next = NULL

When adding at the end, the new last node's next holds whatever garbage malloc left there. Your print loop then walks off into random memory.

3. Using temp->next when temp is NULL

From running a loop one step too far, or skipping the if (head == NULL) guard at the top of a function. Instant segfault.

4. free() before re-routing

Free the node, then try to read toDelete->next to fix the links. That address is no longer yours. Re-route first, free last.

5. Walking with head instead of temp

The loop finishes, head is now NULL, and every node is leaked. Always walk with a copy.

6. Confusing = and ==

if (head = NULL) assigns NULL to head, destroying the list, then evaluates as false. One character, whole list gone.

The same stack, rebuilt out of nodes

This is the payoff for doing the topic in this order. Remember the ADT contract from section 0: a stack promises push, pop, peek, isEmpty. It never promised an array.

So swap the storage. Let top be a pointer instead of an index. Then:

  • push is insert at the front — the operation you already know is two lines.
  • pop is delete the first node — also already written.
struct node *top = NULL;      // "head", renamed for the job it's doing

void push(int item)
{
    struct node *n = (struct node*)malloc(sizeof(struct node));
    if (n == NULL) { printf("Out of memory\n"); return; }

    n->data = item;
    n->next = top;        // attach first
    top     = n;          // then move top     <-- insertFront, exactly
}

int pop()
{
    if (top == NULL) { printf("Underflow\n"); return -1; }

    struct node *temp = top;
    int item = top->data;
    top = top->next;      // re-route
    free(temp);            // then free      <-- deleteFirst, exactly
    return item;
}

int isEmpty() { return top == NULL; }
Look at what disappeared

There is no MAX. There is no overflow check, because there is no ceiling — this stack grows until the machine itself runs out of memory. The bracket checker from Lab 2 works unchanged on a file with a million nested brackets.

And the code that uses the stack never changed at all. That is the ADT idea from section 0, delivered.

Array or linked list?

Both store a sequence. They fail in opposite ways.

ArrayLinked list
In memoryOne contiguous block, like numbered cinema seatsScattered nodes joined by addresses, like scavenger-hunt cards
Get the 5th itemInstant — a[4] is one calculationWalk from the head, four steps
Insert at the frontShift every other element rightTwo pointer assignments, done
SizeFixed when declaredGrows and shrinks while running
Memory costJust the dataData plus a pointer per node
Choose it whenYou know the size and you jump around a lotThe size is unpredictable and you edit the ends often

One line worth memorising: arrays trade flexibility for speed of access; linked lists trade speed of access for flexibility.

Where linked lists actually run

Music and video playlists

Add a song anywhere, remove one, reorder — no shifting. A doubly linked list, with a prev pointer as well, gives you the previous-track button for free.

Image and photo viewers

Next and previous through a folder of unknown size. Circular linking makes the last image wrap to the first.

The memory allocator itself

malloc keeps a linked list of free blocks. Yes — the function you call to build linked lists is itself managing one.

Browser tabs and open files

An unknown number of items, constantly opened and closed in the middle. Exactly the case an array handles badly.
